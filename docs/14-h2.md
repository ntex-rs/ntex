# HTTP/2 with ntex-h2

HTTP/2 in ntex lives in a separate crate, [ntex-h2]. `ntex::http` and
`ntex::web` use it behind the scenes: when a connection negotiates HTTP/2,
ntex hands it to ntex-h2, which takes care of frames, header compression,
streams and flow control, and ntex turns each stream back into the familiar
requests and responses. Most applications never notice the crate is there.

Sometimes, though, you want HTTP/2 itself rather than the general HTTP layer
on top of it. Perhaps you only ever speak HTTP/2, you need trailers or
long-lived bidirectional streams, or you want to control flow control
yourself. gRPC is the classic case: [ntex-grpc](11-grpc.md) uses ntex-h2
directly for both its client and its server, and you can do the same.
ntex-h2 gives you three building blocks:

- **`client::Client`**, a connection pool that opens and reuses connections
  to one server.
- **`client::SimpleClient`**, a client for a single connection that you
  manage yourself.
- **`server::Server`**, an ntex service that handles HTTP/2 connections.

ntex-h2 speaks only HTTP/2 and does not negotiate the protocol, so any
transport you give it must already be committed to HTTP/2. Over TLS, that
means ALPN has selected `h2`. Over plain TCP (h2c), both sides must simply
know in advance. The HTTP/1.1 `Upgrade` mechanism and server push are not
supported.

Here is a client that sends a `GET` request over plain TCP and prints the
response:

```rust,no_run
use ntex::SharedCfg;
use ntex::http::{HeaderMap, Method};
use ntex_h2::{MessageKind, StreamEof, client::Client};

#[ntex::main]
async fn main() -> Result<(), Box<dyn std::error::Error>> {
    let client = Client::builder("127.0.0.1:8080").build(SharedCfg::new("H2-CLIENT"));

    let (_send, recv) = client
        .send(Method::GET, "/index.html".into(), HeaderMap::new(), true)
        .await?;

    while let Some(msg) = recv.recv().await {
        match msg.kind {
            MessageKind::Headers { pseudo, .. } => println!("status: {:?}", pseudo.status),
            MessageKind::Data(data, _) => println!("data: {data:?}"),
            MessageKind::Eof(StreamEof::Data(data, _)) => println!("last data: {data:?}"),
            MessageKind::Eof(_) | MessageKind::Disconnect(_) => break,
        }
    }
    Ok(())
}
```

This is a lower-level API than [`ntex::client`](13-client.md). There are no
URLs, body helpers or `Response` type, only HTTP/2 streams and what travels
on them. The rest of this chapter explains that model first, then covers the
client and the server.

## Streams and messages

An HTTP/2 connection carries many independent streams at once, and each
request shares a stream with its response. The client opens a stream by
sending request headers. Both sides then send data on it, and each closes its
own half when it is done. Either side can also cut a stream short with a
reset, which leaves the connection and its other streams untouched.

In ntex-h2, a stream is represented by a `StreamRef`: a cheap, cloneable
handle that identifies the stream and lets you send on it. Everything that
arrives on a stream reaches you as a `Message`:

```rust,ignore
pub struct Message {
    pub stream: StreamRef,
    pub kind: MessageKind,
}
```

A client and a server see the same kinds of messages:

| `MessageKind` | Meaning |
|---|---|
| `Headers { pseudo, headers, eof }` | A request or response head. `pseudo` holds the pseudo-headers: `method`, `scheme`, `authority`, and `path` on requests, and `status` on responses. If `eof` is `true`, there is no body. |
| `Data(Bytes, Capacity)` | A chunk of the body. `Capacity` is the flow-control credit the chunk used, see [Flow control](#flow-control). |
| `Eof(StreamEof)` | The peer's half of the stream is finished. It ends with `StreamEof::Data` (a last chunk), `StreamEof::Trailers` (trailing headers), or `StreamEof::Error` (the stream failed or was reset). |
| `Disconnect(err)` | The connection failed while the stream was still open. |

Messages always arrive in the same order: one `Headers`, then any number of
`Data`, then exactly one `Eof` or `Disconnect`. If `Headers` has `eof` set,
it is the only message.

Sending works the same way. The headers go first, sent with `send` on a
client or `send_response` on a server. Any number of `send_payload` calls
follow, and the stream ends either with `eof` set on the last one or with
`send_trailers`.

## Configuration

Protocol settings live in `ServiceConfig`. As with other ntex configuration,
you add it to a [`SharedCfg`], and every connection created with that
`SharedCfg` picks it up:

```rust,no_run
use ntex::{SharedCfg, time::Seconds};
use ntex_h2::ServiceConfig;

fn config() -> SharedCfg {
    SharedCfg::new("H2")
        .add(
            ServiceConfig::new()
                .set_max_concurrent_streams(128)
                .set_initial_window_size(256 * 1024)
                .set_initial_connection_window_size(4 * 1024 * 1024)
                .set_ping_timeout(Seconds(30)),
        )
        .into()
}
```

`ServiceConfig` is the same type that `ntex::http` exposes as
[`Http2ServiceConfig`], so the same settings apply to HTTP/2 in an ntex web
server or HTTP client. ntex-h2 connections are ordinary ntex I/O objects, so
an [`IoConfig`] in the same `SharedCfg` controls their buffers and
backpressure, as described in the [I/O chapter](7-io.md).

The settings fall into three groups. The first covers flow control and
frames:

| Setting | Default | Meaning |
|---|---|---|
| `set_initial_window_size` | 64 KiB − 1 | Receive window of each stream: how much body data the peer may send on a stream before it must wait |
| `set_initial_connection_window_size` | 4 MiB | Receive window shared by all streams of a connection |
| `set_max_frame_size` | 16 KiB | Largest frame payload the peer may send. Allowed range is 16 KiB to 16 MiB − 1 |

The second limits what a peer can make you do:

| Setting | Default | Meaning |
|---|---|---|
| `set_max_concurrent_streams` | 256 | Streams the peer may have open at once. Further streams are refused with `REFUSED_STREAM` |
| `set_max_headers` | 96 | Header fields allowed in one header block. A stream with more is refused |
| `set_max_header_list_size` | 48 KiB | Total size of a header block |
| `set_max_header_continuation_frames` | 5 | `CONTINUATION` frames allowed for one header block |
| `set_max_concurrent_reset_streams` | 32 | Recently reset streams remembered so late frames for them are ignored; 0 disables the history |
| `set_reset_stream_duration` | 30 s | How long a reset stream is remembered |
| `set_max_inflight_messages` | 8192 | Messages waiting for your code. When the limit is reached, the connection stops reading until some are handled |

The third sets timeouts:

| Setting | Default | Meaning |
|---|---|---|
| `set_handshake_timeout` | 5 s | Time allowed for the connection preface |
| `set_settings_timeout` | 5 s | Time the peer has to acknowledge a `SETTINGS` frame |
| `set_ping_timeout` | 10 s | Keep-alive interval. If a `PING` is not answered in time, the connection is closed |
| `set_capacity_timeout` | 5 s | Longest a sender waits for flow-control window before the stream is reset; 0 disables it |

Stream limits apply only to streams the peer opens. A server uses
`set_max_concurrent_streams` to cap how many requests a client may run at
once, while a client is bound by whatever limit the server announces.

ntex-h2 also guards against rapid-reset attacks. If at least ten streams have
been opened on a connection and half of them were reset, the connection is
closed with `GOAWAY`.

## The client

### Connecting with a pool

For most programs, `client::Client` is the right choice. It is a pool of
connections to one server: each request goes to a connection that can open
another stream, and a new connection is opened only when none can. Like the
[HTTP client](13-client.md), create it once and keep it for the life of the
application. Clones are cheap and share the same connections.

You create a pool with a builder, and `build` takes the `SharedCfg` for every
connection in the pool:

```rust,no_run
use ntex::{SharedCfg, time::Seconds};
use ntex_h2::{ServiceConfig, client::Client};

fn backend() -> Client {
    let cfg = SharedCfg::new("BACKEND").add(ServiceConfig::new().set_ping_timeout(Seconds(30)));

    Client::builder("backend.internal:8080")
        .connect_timeout(Seconds(3))
        .connection_limit(4)
        .lifetime(Seconds(600))
        .build(cfg)
}
```

The builder has these options:

| Option | Default | Meaning |
|---|---|---|
| `connector` | TCP | The transport connector, for example a TLS connector |
| `secure` | `false` | Sets the `:scheme` of requests to `https` instead of `http` |
| `connect_timeout` | 1 s | Time allowed to connect, including the TLS handshake |
| `minconn` | 1 | Below this many connections, the pool opens a new one for a request even if an existing connection has room |
| `connection_limit` | 16 | Maximum number of connections |
| `max_streams` | 100 | Streams a connection is assumed to accept until the server announces its own limit |
| `lifetime` | not set | Age after which a connection is closed gracefully and replaced |
| `disconnect_timeout` | 15 s | Time a closing connection has to finish its streams |
| `skip_unknown_streams` | off | Ignore frames for streams the client no longer knows instead of treating them as errors |

The pool opens new connections one at a time and spreads requests across
them, preferring connections that use less than half of their stream limit.
When every connection is full and the pool is at its limit, `send` waits for
a stream to free up instead of failing. Errors that happen before a stream is
opened, such as a failed connect or a timeout, are reported as
`ClientError`.

### Secure connections

Over TLS, the pool needs two things: a TLS connector that offers `h2`
through ALPN, and `secure(true)` so that requests carry the `https` scheme.
With OpenSSL:

```rust,no_run
use ntex::SharedCfg;
use ntex_h2::client::Client;
use openssl::ssl::{SslConnector, SslMethod};

fn secure_client() -> Result<Client, openssl::error::ErrorStack> {
    let mut builder = SslConnector::builder(SslMethod::tls())?;
    builder.set_alpn_protos(b"\x02h2")?;

    Ok(Client::builder("api.example.com:443")
        .connector(ntex::tls::openssl::SslConnector::new(builder.build()))
        .secure(true)
        .build(SharedCfg::new("API")))
}
```

The ALPN list `b"\x02h2"` is the protocol name `h2` prefixed with its
length. Unlike `ntex::client`, ntex-h2 cannot fall back to HTTP/1.1, so if
you also offer `http/1.1`, make sure the server will pick `h2`. With rustls,
set `alpn_protocols` to `vec![b"h2".to_vec()]` in its `ClientConfig`.

### A single connection

Sometimes you want to manage connections yourself, for example to pin a
session to one connection, or to run HTTP/2 over a transport you created.
`client::SimpleClient` wraps a single, already established connection:

```rust,no_run
use ntex::{SharedCfg, io::Io, util::ByteString};
use ntex_h2::client::SimpleClient;

async fn connect() -> Result<SimpleClient, Box<dyn std::error::Error>> {
    let cfg: SharedCfg = SharedCfg::new("H2").into();
    let io: Io = ntex::connect::connect_with("127.0.0.1:8080", &cfg).await?;

    Ok(SimpleClient::new(io, false, ByteString::from("127.0.0.1")))
}
```

The arguments are the transport, whether requests use the `https` scheme,
and the `:authority` sent with each request. The connection reads its
`ServiceConfig` from the transport's `SharedCfg`. If you'd rather not do
these steps by hand, `client::Connector` is an ntex service that takes an
address and returns a `SimpleClient`.

`SimpleClient` is cheap to clone. The connection stays open while any clone
exists and closes gracefully when the last one is dropped. You can also close
it earlier:

- `close()` starts a graceful shutdown. Open streams may finish, but no new
  ones can start.
- `force_close()` drops the connection immediately.
- `disconnect().await` closes gracefully and waits until the connection is
  gone. Use `.disconnect_timeout(..)` on the returned future to bound the
  wait.

`is_closed()` and `on_disconnect()` tell you when the connection goes away,
whether you closed it or the server did. A pool handles all of this for you,
but you can still reach a pooled connection: `Client::client()` returns a
`SimpleClient` from the pool that can open another stream.

### Sending a request

`send` starts a request. It takes the method, the `:path` (including any
query string), the headers and an `eof` flag, and returns the two halves of
the new stream: a `SendStream` for the request body and a `RecvStream` for
the response.

```rust,no_run
use ntex::http::{HeaderMap, Method, header};
use ntex::util::Bytes;
use ntex_h2::client::Client;

async fn upload(client: &Client, body: Bytes) -> Result<(), Box<dyn std::error::Error>> {
    let mut headers = HeaderMap::new();
    headers.insert(header::CONTENT_TYPE, header::HeaderValue::from_static("application/octet-stream"));

    let (send, recv) = client.send(Method::POST, "/upload".into(), headers, false).await?;
    send.send_payload(body, true).await?;

    // ... read the response from `recv`
    # drop(recv);
    Ok(())
}
```

Set `eof` to `true` when the request has no body, as with most `GET`
requests. Otherwise, send the body with `send_payload`, which accepts
anything that converts to `Bytes`. Pass `eof: true` on the last call, or
finish with `send_trailers(headers)` if the request has trailers. Since you
can call `send_payload` as often as you like, streaming a large body is just
a loop:

```rust,no_run
# use ntex::util::Bytes;
# use ntex_h2::client::SendStream;
async fn stream_body(
    send: &SendStream,
    chunks: Vec<Bytes>,
) -> Result<(), ntex::error::Error<ntex_h2::OperationError>> {
    for chunk in chunks {
        send.send_payload(chunk, false).await?;
    }
    send.send_payload(Bytes::new(), true).await
}
```

`send_payload` returns once the data has been handed to the connection. It
splits the data into frames that fit both the peer's maximum frame size and
the flow-control window. If the window is closed, it waits for the peer to
reopen it (see [Flow control](#flow-control)). It also waits while the
connection's write buffer is full, so a fast sender cannot outrun the
network.

The request body and the response are independent: you can read the response
while still sending, which is how bidirectional streaming protocols work.
Just make sure only one task sends on a stream at a time.

### Reading the response

`RecvStream` delivers the response as the messages described
[earlier](#streams-and-messages). `recv().await` returns the next message, or
`None` once the response is complete. It also implements `Stream`, if you
prefer stream combinators.

This function collects a whole response:

```rust,no_run
use ntex::http::{HeaderMap, StatusCode};
use ntex::util::{Bytes, BytesMut};
use ntex_h2::{MessageKind, StreamEof, client::RecvStream};

async fn read_response(
    recv: RecvStream,
) -> Result<(StatusCode, HeaderMap, Bytes), Box<dyn std::error::Error>> {
    let mut status = StatusCode::OK;
    let mut headers = HeaderMap::new();
    let mut body = BytesMut::new();

    while let Some(msg) = recv.recv().await {
        match msg.kind {
            MessageKind::Headers { pseudo, headers: hdrs, .. } => {
                status = pseudo.status.unwrap_or(StatusCode::OK);
                headers = hdrs;
            }
            MessageKind::Data(chunk, _capacity) => body.extend_from_slice(&chunk),
            MessageKind::Eof(StreamEof::Data(chunk, _capacity)) => {
                body.extend_from_slice(&chunk);
                break;
            }
            MessageKind::Eof(StreamEof::Trailers(_)) => break,
            MessageKind::Eof(StreamEof::Error(err)) => return Err(err.into()),
            MessageKind::Disconnect(err) => return Err(err.into()),
        }
    }
    Ok((status, headers, body.freeze()))
}
```

Each `Data` message comes with a `Capacity`. Here it is dropped right away,
which lets the server keep sending. Holding on to it is how you slow the
server down, as [Flow control](#flow-control) explains.

### Resets and cancellation

A stream ends early when either side resets it. A reset carries a `Reason`
code from `ntex_h2::frame::Reason`, such as `CANCEL` or `INTERNAL_ERROR`.

To give up on a request, just drop it. Dropping the `RecvStream` before the
response is complete, or the `SendStream` before the request body is
complete, resets the stream with `CANCEL`, and the server can stop working on
it. As a result, a timeout around a request needs no extra code:

```rust,no_run
# use ntex_h2::client::RecvStream;
# async fn read_response(_: RecvStream) -> Result<(), Box<dyn std::error::Error>> { Ok(()) }
# async fn example(recv: RecvStream) {
use ntex::time::{Seconds, timeout};

// If the timeout fires, `recv` is dropped and the stream is reset.
let result = timeout(Seconds(10), read_response(recv)).await;
# }
```

To reset with a specific reason, call `reset(reason)` on the `SendStream` or
the `StreamRef`. `is_reset()` and `on_reset()` tell you whether either side
has reset the stream.

When the server resets a stream, you receive `Eof(StreamEof::Error(..))` and
further sends fail. When the whole connection fails, every open stream gets a
`Disconnect` message instead.

### Stream limits

A server announces how many streams it accepts at once on each connection.
When that limit is reached, `SimpleClient::send` waits until a stream
finishes, while the pool uses another connection or opens a new one.

If you want to check before sending, `SimpleClient` gives you the numbers:
`max_streams()` is the server's limit and `active_streams()` is how many are
in use. `is_ready()` tells you whether another stream can be opened, and
`ready().await` waits until one can. `on_capacity(callback)` registers a
function that runs whenever a stream is released.

Between checking and sending, another task may grab the free stream.
`reserve()` closes that gap: it claims a stream slot immediately and returns
a `StreamReservation`, or `None` if the connection is full. The
reservation's `send` then opens the stream without waiting. Dropping an
unused reservation releases the slot.

## Flow control

HTTP/2 runs many streams over one TCP connection, so TCP's own flow control
is not enough: one slow consumer must not stall every other stream. HTTP/2
adds credit-based flow control on two levels. Every stream has a window, and
the connection has one more, shared by all streams. A window is how many
bytes of body data the sender may still send. Each `DATA` frame uses up part
of both windows, and when either reaches zero, the sender must stop until the
receiver grants more credit with a `WINDOW_UPDATE` frame. Only body data
counts, not headers.

### Receiving data

In ntex-h2, every chunk of body data you receive comes with a `Capacity`,
which stands for the window credit that chunk used up. As long as you hold
the `Capacity`, the credit stays used. When you drop it, or call `consume(n)`
to release part of it, the credit goes back to both the stream's and the
connection's window.

ntex-h2 does not send a `WINDOW_UPDATE` for every released byte. It waits
until enough credit has built up: a third of `initial_window_size` for a
stream, and a quarter of `initial_connection_window_size` for the
connection. With the default stream window of 64 KiB, it goes like this:

1. The server sends 64 KiB on a stream. The stream window drops to zero, and
   the server must wait.
2. Your code receives the data as several `Data` messages, each carrying its
   own `Capacity`.
3. You process the chunks and drop their capacities. Once about 22 KiB has
   been released, ntex-h2 sends a `WINDOW_UPDATE` granting that credit back,
   and the server resumes.
4. If you hold on to the capacities, for example because the data is waiting
   in a queue for a slow consumer, no update is sent and the server stays
   paused.

That last step is what makes `Capacity` useful. It ties the sender's speed to
how fast your code actually processes data, rather than how fast bytes arrive
from the network. Keep the `Capacity` next to the data while it waits, and
drop it only once the data has been handled:

```rust,no_run
use ntex::channel::mpsc;
use ntex::util::Bytes;
use ntex_h2::{Capacity, MessageKind, StreamEof, client::RecvStream};

// Forward the body to a consumer task. The server can only send as fast
// as the consumer drops the capacities.
async fn forward(recv: RecvStream, tx: mpsc::Sender<(Bytes, Capacity)>) {
    while let Some(msg) = recv.recv().await {
        match msg.kind {
            MessageKind::Data(data, cap) => {
                if tx.send((data, cap)).is_err() {
                    break; // consumer is gone, dropping `recv` resets the stream
                }
            }
            MessageKind::Eof(StreamEof::Data(data, cap)) => {
                let _ = tx.send((data, cap));
                break;
            }
            MessageKind::Headers { .. } => {}
            MessageKind::Eof(_) | MessageKind::Disconnect(_) => break,
        }
    }
}
```

Unreleased data also counts against the connection window, which every
stream shares, so a stream that buffers a lot without releasing it can slow
down the others. That is why the connection window is much larger by default
(4 MiB against 64 KiB per stream). Size the two together: the stream window
limits how much a single request can buffer, and the connection window limits
the total across all requests.

Two smaller details:

- Capacities from the same stream can be combined with `+` or `+=`, which is
  handy when you merge several chunks into one buffer. Adding capacities from
  different streams panics.
- `StreamRef::empty_capacity()` creates a zero-sized `Capacity` for a stream,
  a convenient starting value to add chunks to.

If a peer ignores flow control and sends more than the window allows, the
stream fails with `StreamError::RecvWindowExceeded`.

### Sending data

When sending, ntex-h2 tracks the window the peer has granted. `send_payload`
sends as much as the window allows, waits for more credit, and carries on
until all the data is out. Usually that is all you need.

If you produce data on demand, though, it is better to ask first how much the
peer will accept, so you don't generate data that would only sit in memory:

- `available_send_capacity()` returns the current window: the smaller of the
  stream's and the connection's window.
- `send_capacity().await` waits until the window is open and returns its
  size.

```rust,no_run
# use ntex::util::Bytes;
# use ntex_h2::client::SendStream;
# fn produce(_: usize) -> Option<Bytes> { None }
async fn send_generated(send: &SendStream) -> Result<(), ntex::error::Error<ntex_h2::OperationError>> {
    loop {
        let window = send.send_capacity().await? as usize;
        match produce(window) {
            Some(chunk) => send.send_payload(chunk, false).await?,
            None => return send.send_payload(Bytes::new(), true).await,
        }
    }
}
```

A peer that never opens its window would leave a sender waiting forever.
`set_capacity_timeout` prevents that: if a sender waits for capacity longer
than the timeout (5 seconds by default), the stream is reset with `CANCEL`
and the send fails with `StreamError::CapacityTimeout`.

## The server

### Running a server

`server::Server` is an ntex service that takes an I/O object and serves
HTTP/2 on it until the connection closes. You run it like any other ntex
service, with `ntex::server::build()` (see the [server chapter](5-server.md)):

```rust,no_run
use ntex::http::{HeaderMap, StatusCode};
use ntex::{SharedCfg, error::Error};
use ntex_h2::{Message, MessageKind, OperationError, ServiceConfig, server};

#[ntex::main]
async fn main() -> std::io::Result<()> {
    let cfg = SharedCfg::new("H2-SRV").add(ServiceConfig::new().set_max_concurrent_streams(100));

    ntex::server::build()
        .bind("h2", "127.0.0.1:8080", cfg, async |_| {
            server::Server::new(async |msg: Message| {
                if let MessageKind::Headers { pseudo, .. } = msg.kind {
                    println!("{:?} {:?}", pseudo.method, pseudo.path);
                    msg.stream.send_response(StatusCode::OK, HeaderMap::new(), false)?;
                    msg.stream.send_payload("hello world", true).await?;
                }
                Ok::<_, Error<OperationError>>(())
            })
        })?
        .run()
        .await
}
```

The connections take their `ServiceConfig` from the `SharedCfg` passed to
`bind`. Since this listener accepts plain TCP, clients must use prior
knowledge, for example `curl --http2-prior-knowledge http://127.0.0.1:8080/`.

For TLS, put a TLS acceptor in front of the server and have it select `h2`
during ALPN:

```rust,no_run
use ntex::{Service, SharedCfg, error::Error};
use ntex::tls::openssl::SslAcceptor;
use ntex_h2::{Message, OperationError, server};
use openssl::ssl::{self, AlpnError, SslFiletype, SslMethod};

#[ntex::main]
async fn main() -> std::io::Result<()> {
    let mut builder = ssl::SslAcceptor::mozilla_intermediate(SslMethod::tls()).unwrap();
    builder.set_private_key_file("key.pem", SslFiletype::PEM).unwrap();
    builder.set_certificate_chain_file("cert.pem").unwrap();
    builder.set_alpn_select_callback(|_, protos| {
        if protos.windows(3).any(|w| w == b"\x02h2") {
            Ok(b"h2")
        } else {
            Err(AlpnError::NOACK)
        }
    });
    let acceptor = builder.build();

    ntex::server::build()
        .bind("h2", "127.0.0.1:8443", SharedCfg::new("H2-TLS"), async move |_| {
            SslAcceptor::new(acceptor.clone())
                .map_err(|e| server::ServerError::from(std::io::Error::other(e)))
                .and_then(server::Server::new(async |_msg: Message| {
                    // handle messages
                    Ok::<_, Error<OperationError>>(())
                }))
        })?
        .run()
        .await
}
```

If you already have an I/O object, say from your own acceptor or from a
connection that switched protocols, `server::handle_one(io, publish,
control)` serves it directly with services you have already created. That is
how ntex-grpc runs its server.

### Handling streams

The function or service you pass to `Server::new` is the *publish* service,
and a new one is created for every connection. ntex-h2 calls it for every
message on every stream the client opens: once for the request headers, once
for each chunk of body data, and once for the end of the stream.

These calls run concurrently; ntex-h2 does not wait for one to finish before
starting the next. That keeps a slow request from holding up the others, but
it changes how you write the service. You cannot `await` the request body in
the call that received the headers, because the body arrives in calls of its
own. Instead, the publish service keeps per-stream state and routes each
message to where it is needed.

A simple way to do that is a map keyed by `StreamRef`, which implements
`Hash` and `Eq`. The service below collects each request body, up to a size
limit, and echoes it back once the request is complete:

```rust,no_run
use std::{cell::RefCell, collections::HashMap};

use ntex::http::{HeaderMap, StatusCode};
use ntex::service::{Ctx, Service};
use ntex::util::BytesMut;
use ntex_h2::{Message, MessageKind, OperationError, StreamEof, StreamRef, frame::Reason};

const MAX_BODY: usize = 1024 * 1024;

#[derive(Default)]
struct Echo {
    bodies: RefCell<HashMap<StreamRef, BytesMut>>,
}

impl Service<(), Message> for Echo {
    type Res = ();
    type Error = ntex::error::Error<OperationError>;

    async fn call(&self, msg: Message, _: Ctx<'_, Self, ()>) -> Result<(), Self::Error> {
        let Message { stream, kind } = msg;

        let body = match kind {
            MessageKind::Headers { eof: true, .. } => BytesMut::new(),
            MessageKind::Headers { .. } => {
                self.bodies.borrow_mut().insert(stream, BytesMut::new());
                return Ok(());
            }
            MessageKind::Data(data, _) => {
                let mut bodies = self.bodies.borrow_mut();
                if let Some(body) = bodies.get_mut(&stream) {
                    body.extend_from_slice(&data);
                    if body.len() > MAX_BODY {
                        bodies.remove(&stream);
                        stream.reset(Reason::CANCEL);
                    }
                }
                return Ok(());
            }
            MessageKind::Eof(StreamEof::Data(data, _)) => {
                let Some(mut body) = self.bodies.borrow_mut().remove(&stream) else {
                    return Ok(());
                };
                body.extend_from_slice(&data);
                body
            }
            MessageKind::Eof(StreamEof::Trailers(_)) => {
                let Some(body) = self.bodies.borrow_mut().remove(&stream) else {
                    return Ok(());
                };
                body
            }
            MessageKind::Eof(StreamEof::Error(_)) | MessageKind::Disconnect(_) => {
                self.bodies.borrow_mut().remove(&stream);
                return Ok(());
            }
        };

        stream.send_response(StatusCode::OK, HeaderMap::new(), false)?;
        stream.send_payload(body.freeze(), true).await
    }
}
```

The `RefCell` is never borrowed across an `await`, because other calls on
the same service run in between. Removing the entry on
`Eof(StreamEof::Error(..))` and `Disconnect` keeps the map from leaking when
a client goes away mid-request.

To use a service type like this, wrap it in a factory. `fn_factory` takes an
async function and calls it for each new connection:

```rust,no_run
# use ntex::service::{Ctx, Service};
# use ntex_h2::{Message, OperationError};
# #[derive(Default)] struct Echo;
# impl Service<(), Message> for Echo {
#     type Res = ();
#     type Error = ntex::error::Error<OperationError>;
#     async fn call(&self, _: Message, _: Ctx<'_, Self, ()>) -> Result<(), Self::Error> { Ok(()) }
# }
use ntex::service::fn_factory;
use ntex_h2::server;

# fn server() -> server::Server<ntex::io::IoBoxed, ntex::error::Error<OperationError>, std::convert::Infallible> {
server::Server::new(fn_factory(async |_: &()| {
    Ok::<_, std::convert::Infallible>(Echo::default())
}))
# }
```

Buffering works for small bodies. For large or streaming bodies, store a
channel sender in the map instead and pass each chunk to a task that handles
the request. Send the `Capacity` along with the data, as in the
[flow control](#flow-control) example, so the client slows down to that
task's pace. This is how `ntex::http` builds request payloads on top of
ntex-h2.

### Sending the response

You respond through the request's `StreamRef`:

- `send_response(status, headers, eof)` sends the response head. Set `eof` to
  `true` if there is no body.
- `send_payload(data, eof)` sends body data, exactly as on the client.
- `send_trailers(headers)` ends the stream with trailing headers. gRPC uses
  these to carry its status.
- `send_informational(status, headers)` sends a 1xx response, such as
  `103 Early Hints`, before the final one.

You don't have to respond from the call that received the request.
`StreamRef` is cloneable, so you can store it or move it into another task
and respond later. The client's flow-control helpers,
`available_send_capacity` and `send_capacity`, are available on `StreamRef`
too.

### Errors and resets

An error can affect one stream or the whole connection, so choose
carefully.

To fail a single request, send an error response or reset its stream with
`stream.reset(reason)`. The connection and its other streams carry on.
`REFUSED_STREAM` tells the client it may safely retry, while `CANCEL` or
`INTERNAL_ERROR` tell it the request failed.

Returning an error from the publish service is far more drastic. ntex-h2
treats it as a fault in the connection itself: it sends `GOAWAY` with
`INTERNAL_ERROR` and closes the connection, failing every stream on it. It is
still fine to use `?` on `send_response` and `send_payload`, because they
fail only when the stream or connection is already gone. For problems with a
request, reset the stream instead.

If the client resets a stream while one of your calls for it is still
running, that call is cancelled. You still receive an `Eof` message with the
error, so you can clean up per-stream state as shown above.

### The control service

Connection-level events go to a second service, the *control* service. The
default accepts everything, and most servers never replace it. To log or
react to connection events, pass your own to `.control(..)`:

```rust,no_run
use ntex::error::Error;
use ntex_h2::{Control, Message, OperationError, server};

# fn server() -> server::Server<ntex::io::IoBoxed, Error<OperationError>, std::io::Error> {
server::Server::new(async |_msg: Message| Ok::<_, Error<OperationError>>(()))
    .control(async |msg: Control<Error<OperationError>>| {
        if let Control::Disconnect(reason) = &msg {
            log::info!("connection closed: {reason:?}");
        }
        Ok::<_, std::io::Error>(msg.ack())
    })
# }
```

`Control::Disconnect` tells you why a connection ended: a protocol error, a
`GOAWAY` from the client, the client going away, or an error returned by the
publish service. Answer every control message with `msg.ack()`.

### Server state

The publish and control services run in pipelines whose state is the
*connection state*: a value that travels with the I/O object, as described in
[Carrying state with a request](3-state.md#carrying-state-with-a-request).
A plain `Io` carries no state, so the state is `()`. That is why `Echo`
above implements `Service<(), Message>` and its factory takes `&()`.

The worker state, created by `build_with_config()` (see
[Worker and request state](6-server-app.md)), is not passed to these
services. To make it available, put a service in front of `Server` that reads
the worker state and returns the connection wrapped in a `State`, together
with whatever the handlers need. That service can also record details about
the connection, such as the peer address. ntex-h2 clones the connection state
for the publish and control factories, so it must implement `Clone`. Keep
shared resources behind an `Rc`.

Handlers can then be [state-aware functions](3-state.md#state-aware-functions)
that take the connection state as their first argument, and service
factories receive it in `create`:

```rust,no_run
use std::{cell::Cell, convert::Infallible, net::SocketAddr, rc::Rc};

use ntex::http::{HeaderMap, StatusCode};
use ntex::io::{Io, types::PeerAddr};
use ntex::service::{State, service};
use ntex::{SharedCfg, error::Error};
use ntex_h2::{Message, MessageKind, OperationError, server};

/// Worker state, created once per worker.
#[derive(Clone)]
struct AppState {
    requests: Rc<Cell<u64>>,
}

/// Connection state, shared by all streams of one connection.
#[derive(Clone)]
struct Conn {
    app: AppState,
    peer: Option<SocketAddr>,
}

async fn accept(
    app: &AppState,
    io: Io,
) -> Result<State<Conn, Io>, server::ServerError<Infallible>> {
    let peer = io.query::<PeerAddr>().get().map(|addr| addr.into_inner());
    let conn = Conn { app: app.clone(), peer };
    Ok(State { req: io, state: conn })
}

async fn publish(conn: &Conn, msg: Message) -> Result<(), Error<OperationError>> {
    if let MessageKind::Headers { pseudo, .. } = msg.kind {
        let requests = &conn.app.requests;
        requests.set(requests.get() + 1);
        println!("{:?} from {:?}, request #{}", pseudo.path, conn.peer, requests.get());

        msg.stream.send_response(StatusCode::OK, HeaderMap::new(), false)?;
        msg.stream.send_payload("hello world", true).await?;
    }
    Ok(())
}

#[ntex::main]
async fn main() -> std::io::Result<()> {
    ntex::server::build_with_config(async || {
        Ok(AppState {
            requests: Rc::new(Cell::new(0)),
        })
    })
    .bind("h2", "127.0.0.1:8080", SharedCfg::default(), async |_: &AppState| {
        service(accept).and_then(server::Server::new(publish))
    })?
    .run()
    .await
}
```

Each worker has its own `AppState`, so `requests` counts only the requests
handled by that worker. Use an `Arc` for values that must be shared across
workers. Per-stream state, such as a request body that is still arriving,
belongs in the publish service itself, as in the `Echo` example.

With `handle_one`, you create the publish and control pipelines yourself,
so they hold whatever state you gave them.

### Shutting down

When the ntex server stops, its workers wait for connections to finish, as
described in the [server chapter](5-server.md). To wind down HTTP/2
connections in an orderly way, call `ServiceConfig::shutdown()`. From then
on, servers on the current thread refuse new streams, let active ones finish,
and close their connections.

### What you take on

`ntex::http` does more than relay frames. It checks that a body matches its
`content-length`, enforces body size limits, guards against floods of empty
`DATA` frames, and maps everything onto requests and responses. With ntex-h2
on its own, those policies are up to you. That freedom is the reason to use
it directly, but plan for the extra work.

## Summary

- ntex-h2 is the HTTP/2 implementation behind `ntex::http` and `ntex::web`.
  Use it directly, as ntex-grpc does, when you want HTTP/2 only, with full
  control over streams, trailers and flow control.
- The protocol must already be negotiated: ALPN `h2` over TLS, or prior
  knowledge over plain TCP.
- Configure connections with `ServiceConfig` in a `SharedCfg`. It is the same
  type as `ntex::http`'s `Http2ServiceConfig`.
- On the client, keep one `client::Client` pool per server, or use
  `SimpleClient` to manage a single connection. `send` returns a `SendStream`
  for the request body and a `RecvStream` for the response.
- Dropping either half of an unfinished request resets the stream with
  `CANCEL`, so timeouts and cancellation need no extra code.
- Received data comes with a `Capacity`. Holding it keeps the peer waiting,
  and dropping it lets the peer send more. Pass it along with the data to
  apply backpressure.
- On the server, the publish service is called concurrently for every
  message, so keep per-stream state keyed by `StreamRef`. Reset a stream to
  fail one request. Return an error only to close the whole connection.

For a complete program, see the [HTTP/2 example]: a server with buffered and
streaming request bodies, backpressure and trailers, plus a client that calls
it. The [ntex-h2 examples] and the [gRPC chapter](11-grpc.md) have more.
