# Web Application Extractors and Responders

Most handlers do not need to parse requests or build responses by hand. ntex
handles both sides of the process:

- **Extractors** provide the values passed to a handler.
- **Responders** turn the handler's result into an HTTP response.

This leaves the handler free to focus on application logic.

## Extractors

Handler arguments are extractors. Before calling a handler registered with
[`Route::to()`], ntex creates each argument from the request in the order it
appears in the function signature. Each argument type must implement
[`FromRequest`].

The built-in extractors cover common request data:

| Extractor | Reads |
|---|---|
| [`HttpRequest`] | Request metadata, headers, and connection information |
| [`Path<T>`] | Dynamic path segments |
| [`Query<T>`] | URL query parameters |
| [`Json<T>`] | A JSON request body |
| [`Form<T>`] | A URL-encoded request body |
| [`Payload`] | The streaming request body |
| [`Bytes`] | The complete request body as bytes |
| `String` | The complete request body as decoded text |

For example, this handler reads a user ID from the path and an optional flag
from the query string:

```rust
use ntex::web::{self, App};

#[derive(serde::Deserialize)]
struct Options {
    details: Option<bool>,
}

async fn user(
    user_id: web::types::Path<u32>,
    options: web::types::Query<Options>,
) -> String {
    format!(
        "User {}, details: {}",
        user_id.into_inner(),
        options.details.unwrap_or(false),
    )
}

App::default().route(
    "/users/{user_id}",
    web::get().to(user),
);
```

If any extractor fails, the handler is not called. ntex turns the error into a
response through [`WebResponseError`].

### Request Bodies

A request has only one body stream, and all extractors share it. `Json<T>`,
`Form<T>`, `Bytes`, and `String` consume that stream, so a handler should
normally have only one body extractor.

`Json<T>`, `Form<T>`, and `Query<T>` use `serde` to deserialize values.
`Path<T>` can read path variables by order into a tuple or by name into a
struct.

Use [`JsonConfig`], [`FormConfig`], and [`PayloadConfig`] to change body limits
or accepted content types. Store the configuration in [`WebAppConfig`] and
install it with [`App::with_config()`].

### Optional Extractors

Sometimes invalid input should not stop the request. Wrapping an extractor in
`Option<T>` turns a successful extraction into `Some(value)` and a failure
into `None`. The failure is also logged:

```rust
use ntex::web::{self, App};

#[derive(serde::Deserialize)]
struct Search {
    query: String,
}

async fn search(params: Option<web::types::Query<Search>>) -> String {
    match params {
        Some(params) => format!("Searching for {}", params.query),
        None => "No search query".to_owned(),
    }
}

App::default().route("/search", web::get().to(search));
```

If the handler needs the actual error, use `Result<T, T::Error>` instead. Both
forms allow the handler to run when extraction fails.

### Custom Extractors

You can turn application-specific request data into a handler argument by
implementing [`FromRequest`]. A custom extractor receives the application
state, the HTTP request, and mutable access to the request body:

```rust
use ntex::http::Payload;
use ntex::web::{self, App, FromRequest, HttpRequest, InternalError};

struct ClientName(String);

impl<St: web::State> FromRequest<St> for ClientName {
    type Error = InternalError<&'static str>;

    async fn from_request(_: &St, req: &HttpRequest, _: &mut Payload) -> Result<Self, Self::Error> {
        req.headers()
            .get("x-client-name")
            .and_then(|value| value.to_str().ok())
            .map(|value| ClientName(value.to_owned()))
            .ok_or_else(|| web::error::ErrorBadRequest("Missing client name"))
    }
}

async fn hello(client: ClientName) -> String {
    format!("Hello, {}!", client.0)
}

App::default().route("/", web::get().to(hello));
```

Handlers registered with [`Route::to_with_state()`] receive the application
state and request-local state before their extractor arguments. Extractors
otherwise behave in the same way. See [Web Application State](./8.2-web-app.md) for details.

## Responders

Handler return values are responders. Any type that implements [`Responder`]
can be returned from a handler, and ntex turns it into an HTTP response.

Common responder types include:

| Responder | Result |
|---|---|
| [`HttpResponse`] or `HttpResponseBuilder` | The response as configured |
| `String` or `&'static str` | `200 OK` with a plain-text body |
| `Bytes` or `&'static [u8]` | `200 OK` with a binary body |
| `Json<T>` | `200 OK` with a JSON body |
| `Form<T>` | `200 OK` with a URL-encoded body |
| `Option<T>` | The inner response, or `404 Not Found` for `None` |
| `Result<T, E>` | The inner response, or the response produced by `E` |
| `(T, StatusCode)` | The inner response with a different status code |

Use [`Responder::with_status()`] and [`Responder::with_header()`] when you only
need to change the status or add a header:

```rust
use ntex::http::StatusCode;
use ntex::web::{self, App, Responder};

#[derive(serde::Serialize)]
struct User {
    id: u32,
}

async fn create_user() -> impl Responder {
    web::types::Json(User { id: 42 })
        .with_status(StatusCode::CREATED)
        .with_header("x-api-version", "1")
}

App::default().route(
    "/users",
    web::post().to(create_user),
);
```

### Custom Responders

Implement [`Responder`] when one of your own types should be returned directly
from a handler:

```rust
use ntex::http::Response;
use ntex::web::{self, App, HttpRequest, Responder};

struct Greeting(&'static str);

impl<St: web::State> Responder<St> for Greeting {
    async fn respond_to(self, _: &St, _: &HttpRequest) -> Response {
        Response::Ok()
            .content_type("text/plain; charset=utf-8")
            .body(self.0)
    }
}

async fn hello() -> Greeting {
    Greeting("Hello!")
}

App::default().route("/", web::get().to(hello));
```
