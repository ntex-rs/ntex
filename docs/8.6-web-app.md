# WebSocket Support

HTTP works in one direction: the client asks, and the server answers. WebSocket
removes that limit. Once a connection is open, either side can send a message
whenever it likes. That makes it a natural fit for chat, live notifications,
and other interactive applications. It can also carry a different protocol,
such as MQTT, over an ordinary web connection.

## WebSocket support in ntex

Every WebSocket connection starts life as an HTTP/1.1 request. The client asks
to upgrade the connection, and the server agrees by replying with
`101 Switching Protocols`. From then on, the two sides stop speaking HTTP and
exchange WebSocket frames instead. A `ws://` URL means a plain connection;
`wss://` means the same thing over TLS. The APIs in this chapter work with
HTTP/1 upgrades, not HTTP/2 extended CONNECT.

ntex gives you four ways to work with WebSocket. Most web applications only
need the first:

| API | Use it to |
| --- | --- |
| [`web::ws`] | Add a WebSocket endpoint to a routed web application |
| [`HttpService`] and HTTP/1 control services | Take over an upgraded connection and drive it yourself |
| [`ws::WsClient`] | Connect to a WebSocket server |
| [`ws::WsTransport`] | Run a byte-oriented protocol over binary WebSocket messages |

All four share the codec and protocol types in [`ntex::ws`]. WebSocket support
is on by default through the `ws` Cargo feature. For `wss://`, you'll also need
a configured TLS connector, using a backend such as OpenSSL, rustls, or Windows
Schannel. Changing the URL alone does not enable TLS on `WsClient`; see
[WebSocket TLS configuration](10-tls.md#websocket-client). The optional `compress`
feature adds `permessage-deflate` support to the codec and the client. Note
that `web::ws::start()` doesn't negotiate compression on its own.

### Frames, messages, and fragmentation

You receive data as a [`Frame`] and send data as a [`Message`]. Both have
variants for text, binary, ping, pong, close, and continuation frames.

A sender can split one message into several frames. When that happens, you'll
first see `Frame::Continuation(Item::FirstText(_))` or `FirstBinary(_)`, then
zero or more `Continue(_)` fragments, and finally `Last(_)`. The codec makes
sure the fragments arrive in a valid order, but it doesn't join them for you.
If your handler needs whole messages, it has to collect the fragments itself
or reject fragmented input.

Two more things to watch for:

- Text frames are delivered as raw bytes, but the codec checks that each
  text message is valid UTF-8 and fails the connection otherwise. A
  multi-byte character can be split between two fragments, so convert the
  joined message to a string, not each fragment. `Codec::validate_utf8(false)`
  turns the check off.
- The codec limits each frame to 64 KiB (`Codec::max_size()`) and each
  message, all fragments together, to 4 MiB (`Codec::max_message_size()`).
  A larger frame or message fails with `ProtocolError::Overflow`. To accept a
  single-frame message over 4 MiB, raise both limits.

## Servers with `web::ws`

A WebSocket endpoint starts out as an ordinary route with a GET handler.
Inside the handler, call [`web::ws::start`] with the request and a service for
incoming frames. For each frame, the service returns `Some(Message)` to send a
reply, or `None` to send nothing.

Here is a complete echo server. It handles text and binary messages that
arrive in a single frame:

```rust,no_run
use std::io;

use ntex::web::{self, HttpRequest, ws};

async fn echo(frame: ws::Frame) -> Result<Option<ws::Message>, io::Error> {
    let message = match frame {
        ws::Frame::Text(bytes) => match String::from_utf8(bytes.to_vec()) {
            Ok(text) => ws::Message::Text(text.into()),
            Err(_) => ws::Message::Close(Some(ws::CloseCode::Invalid.into())),
        },
        ws::Frame::Binary(bytes) => ws::Message::Binary(bytes),
        ws::Frame::Ping(bytes) => ws::Message::Pong(bytes),
        ws::Frame::Pong(_) => return Ok(None),
        ws::Frame::Close(reason) => ws::Message::Close(reason),
        ws::Frame::Continuation(_) => {
            ws::Message::Close(Some(ws::CloseCode::Unsupported.into()))
        }
    };
    Ok(Some(message))
}

async fn socket(req: HttpRequest) {
    if let Err(err) = ws::start(&req, None, echo).await {
        eprintln!("WebSocket connection failed: {err:?}");
    }
}

#[ntex::main]
async fn main() -> io::Result<()> {
    web::server(async |_| {
        web::App::new().route("/ws/", web::get().to(socket))
    })
    .bind("127.0.0.1:8080", ntex::SharedCfg::default())?
    .run()
    .await
}
```

Notice that the handler doesn't build an HTTP response. `start()` validates
the handshake, sends the `101` response, and takes the connection away from
the HTTP layer. It then runs the WebSocket dispatcher until the connection
closes, so the `await` lasts as long as the connection does, not just until
it's set up.

During the handoff, `start()` also cancels the HTTP layer's read timer and
switches to an I/O configuration without idle keepalive. If the handshake is
invalid, `start()` sends the HTTP error response itself. Once the connection
has been taken over, returning an `HttpResponse` from your handler won't send
anything else.

If the connection fails, `start()` returns a [`WsError`]. That covers errors
from your frame service, protocol errors, read and write timeouts, and I/O
errors.

### Sending outside the frame handler

Returning a message is the easiest way to reply to a frame. Sometimes, though,
you need to send something unprompted, such as a notification produced by
another task. That's what a [`WsSink`] is for.

The frame service receives the sink as its state. Use `fn_service_st`, or
implement `Service<WsSink, Frame>` yourself, to get at it.

A `WsSink` is cheap to clone, and every clone sends to the same connection.
Give a clone to any task that needs to push messages to the client, such as
a timer, a pub/sub subscription, or a chat room broadcaster. Each task can
then call `sink.send(...)` on its own, independently of the frame handler and
of each other. The clones also share the connection's state: once any of them
sends a close message, no more messages can be sent through any of them.

The sink is reference-counted with `Rc`, so it stays on the connection's
worker thread. Start those tasks with `ntex::rt::spawn` from the same worker,
not on a separate thread.

This service answers pings through the sink instead of returning the pong:

```rust
use std::io;
use ntex::service::fn_service_st;
use ntex::web::ws;

let service = fn_service_st(async |sink: &ws::WsSink, frame: ws::Frame| {
    if let ws::Frame::Ping(bytes) = frame {
        sink.send(ws::Message::Pong(bytes))
            .await
            .map_err(io::Error::other)?;
    }
    Ok::<Option<ws::Message>, io::Error>(None)
});
```

The pong has already been sent, so the handler returns `None`. Returning it as
well would send it twice. `send()` also waits while the connection is under
write backpressure. If your application keeps its own queue of outgoing
messages, give that queue a limit so a slow client can't make it grow forever.

The [basic WebSocket example] uses a sink for its heartbeat. It comes with a
browser page, a Rust client, and the server. The server's readiness hook
starts the heartbeat task once, and its shutdown hook stops it. The task
sends pings and keeps track of when the client last sent a ping or pong. If
the client goes quiet for too long, the task closes the connection.

### Choosing a subprotocol

A subprotocol tells both peers what the connection will carry. `mqtt`, for
example, means the connection carries MQTT. The client lists the protocols it
supports, and the server picks one. Read the client's offers with
[`web::ws::subprotocols`] and pass your choice to `start()`:

```rust
let chosen = ntex::web::ws::subprotocols(&req)
    .find(|protocol| *protocol == "my-application");
ntex::web::ws::start(&req, chosen, service).await?;
```

Whatever you pass as `Some(protocol)` must be a valid token that the client
actually offered. `None` accepts the connection without a subprotocol. That's
fine if your application doesn't need one. If it does, reject clients that
don't offer a protocol you support.

Keep in mind that the handshake only checks the WebSocket protocol. It says
nothing about who is allowed to connect. Authenticate the client, and check
the `Origin` header for browser clients, before you call `start()`.

### Heartbeats and closing the connection

Ping, pong, and close frames reach your frame service just like data frames.
`start()` takes care of dispatcher control and shutdown events, but it does
**not** answer pings. Your service has to return or send the pong, as the echo
handler does.

When the peer sends a close frame, reply with a close of your own unless
you've already sent one. Once your service has handled the peer's close,
`start()` closes the I/O stream.

To close the connection from your side, return or send `Message::Close`. That
starts the closing-handshake timeout. You can set it with
`WsClientConfig::set_close_timeout()` in the connection's shared
configuration; despite the name, it applies to server-side sinks too.

Background tasks such as a heartbeat should stop when the connection ends,
as they do in the basic example. If a peer stops responding, or the
connection has to go for some other reason, call `sink.io().close()` instead
of waiting for the application to exchange more messages.

If you want to handle dispatcher events yourself, use
[`web::ws::start_with`]. It performs the same upgrade, but your service
receives `DispatchItem<WsSink>` instead of `Frame`. That makes it responsible
for control and stop events too, including errors and shutdown.

## Low-level servers with an HTTP control service

You don't need a web application to accept WebSocket connections. If you're
building a lower-level server, sharing one listener between several
protocols, or running your own I/O loop, you can handle the upgrade in an
HTTP control service.

Attach the control service with `HttpService::h1(...).control(...)`, or with
`HttpService::new(...).h1_control(...)` if you're using the combined HTTP
service.

Upgrade requests reach the control service as [`h1::Control::Upgrade`]. You
can look at the request before deciding what to do with it, so this is the
place to check the path, authentication, `Origin`, and any subprotocol you
require. [`ws::handshake`] validates the WebSocket handshake and returns a
response builder. Authorization and subprotocol selection are still up to
you.

You have three choices:

- Reject the request with `upgrade.fail(error)` or
  `upgrade.fail_with(response)`.
- Pass it on to the regular application service with `upgrade.ack()`. This is
  the path a `web::ws` handler relies on.
- Take over the connection with `upgrade.handle()`.

`handle()` gives you the acknowledgement to return, the I/O stream, the
request, and the HTTP/1 codec. This excerpt from the
[low-level WebSocket example] passes everything except the acknowledgement to
a separate `ws_service`:

```rust
.h1_control(async move |control: h1::Control<_, _>| {
    let ack = if let h1::Control::Upgrade(upgrade) = control {
        let (ack, io, request, http_codec) = upgrade.handle();
        ws_service.call((request, io, http_codec)).await?;
        ack
    } else {
        control.ack()
    };
    Ok::<_, io::Error>(ack)
})
```

`ws_service` checks the handshake and writes the HTTP response with the codec
it received. Only then does it switch to `ws::Codec::new()` for WebSocket
frames. A codec created this way follows the server's masking rules; a client
would need the client rules instead.

`handle()` only transfers ownership. It doesn't send a response, so your code
must send either an HTTP rejection or the `101` response. Keep using the I/O
stream you were given: it may already hold the start of the first WebSocket
frame, buffered right after the HTTP headers.

At this level, the connection's lifetime is your responsibility too:

- Stop the HTTP timer with `io.stop_timer()` and choose I/O settings for the
  new protocol. Otherwise the old header-read timer can fire in the middle of
  the WebSocket session.
- Drive the connection with `io.recv()` / `io.send()` or an I/O dispatcher.
  Your loop must handle ping/pong, fragmented messages, close frames, and
  protocol and transport errors.
- Finish the closing handshake, shut down the I/O stream, and stop any
  background tasks that belong to the connection.

The example changes the I/O settings with `Io::set_config()`. This call is
unsafe: no reference borrowed from the old configuration may still be alive
when you make it. The [I/O chapter](./7-io.md) explains why.

The complete example puts all of this together with an OpenSSL acceptor and a
web application that serves static files for ordinary HTTP requests. Its
WebSocket loop echoes text and binary frames, answers pings, and uses pongs
for its heartbeat. It rejects fragmented messages instead of assembling them.
The example's README lists the server and client commands and explains how
to set up the test certificate.

## Clients with `ntex::ws`

To connect to a WebSocket server, create a [`WsClient`] and call
`connect().await`. Client settings go in a [`WsClientConfig`] inside a
`SharedCfg`. When the handshake succeeds, you get a [`WsConnection`], which
holds the server's response and a sink for sending messages.

This client connects to the echo server above, sends `"hello"`, prints the
reply, and closes the connection:

```rust,no_run
use std::io;

use futures::StreamExt;
use ntex::{SharedCfg, time::Seconds, ws};

#[ntex::main]
async fn main() -> io::Result<()> {
    let cfg = SharedCfg::new("WS-CLIENT").add(
        ws::WsClientConfig::new()
            .set_max_frame_size(128 * 1024)
            .set_handshake_timeout(Seconds(5))
            .set_close_timeout(Seconds(5)),
    );
    let connection = ws::WsClient::new("ws://127.0.0.1:8080/ws/", cfg)
        .connect()
        .await
        .map_err(io::Error::other)?;
    println!("Handshake: {}", connection.response().status());

    let sink = connection.sink();
    let mut frames = connection.seal().receiver();
    sink.send(ws::Message::Text("hello".into()))
        .await
        .map_err(io::Error::other)?;

    while let Some(frame) = frames.next().await {
        match frame.map_err(|err| io::Error::other(format!("{err:?}")))? {
            ws::Frame::Text(bytes) => {
                println!("Echo: {bytes:?}");
                sink.send(ws::Message::Close(Some(ws::CloseCode::Normal.into())))
                    .await
                    .map_err(io::Error::other)?;
            }
            ws::Frame::Ping(bytes) => {
                sink.send(ws::Message::Pong(bytes))
                    .await
                    .map_err(io::Error::other)?;
            }
            ws::Frame::Close(_) => break,
            _ => {}
        }
    }
    Ok(())
}
```

The client reads frames through `receiver()`, using `futures::StreamExt` just
like the [basic WebSocket client]. `seal()` erases the concrete I/O filter
type. `receiver()` then starts the dispatcher in a background task and returns
a channel of frames and errors.

The receiver replies to the server's close frame for you, and dropping the
receiver starts the closing handshake. Pings are different: they still show
up in your loop, and you have to send the pong yourself.

If you'd rather use a frame service than a channel, call
`connection.seal().start(service).await`. The service works like the
server-side one, except that its state is `()` rather than a sink. It still
returns `Option<Message>`, and it has to reply to both pings and close frames.
Be sure to await or spawn `start()`; holding on to the connection or a sink
doesn't run the dispatcher.

### Configuration and TLS

`WsClientConfig` is where you offer subprotocols, add headers such as `Origin`
or authentication, limit frame and message sizes
(`set_max_frame_size`, `set_max_message_size`), and set the handshake and close
timeouts. The handshake timeout starts after the connection is established
and covers only the HTTP exchange. If you need a deadline for the whole
operation, wrap it in your own timeout.

If the server selects a subprotocol, the client checks that it's valid and
was one of the offers. A server may also accept without selecting one. If
your application depends on a particular subprotocol, check the response
before sending any data.

For `wss://`, enable the matching Cargo feature and configure a TLS connector
with `WsClient::openssl()` or `WsClient::rustls()`. The [low-level TLS client]
shows an OpenSSL setup that works with a local self-signed certificate. It
turns off certificate verification for the demo; a real client must verify
the server's certificate and hostname.

With the `compress` feature, `set_deflate(DeflateConfig::new())` offers
`permessage-deflate` compression. The server can accept or decline the offer,
so turning it on doesn't guarantee a compressed connection.

## WebSocket as a byte transport

Sometimes you don't care about WebSocket messages at all; you just want to run
another protocol over the connection. MQTT, for example, already knows how to
decode its packets, acknowledge messages, and keep the connection alive. It
shouldn't also have to deal with WebSocket frames.

[`WsTransport`] keeps the two apart. It's an I/O filter that strips binary
WebSocket framing from incoming data and adds it to outgoing data:

```text
socket <-> optional TLS <-> WebSocket filter <-> MQTT or another byte protocol
```

The protocol on top sees the bytes from binary messages and their
continuation fragments. Text messages are rejected. Unlike the frame services
above, the filter answers pings itself, ignores pongs, and takes part in the
closing handshake when the I/O stream shuts down.

**The result is a byte stream, not a stream of messages.** One protocol packet
can be spread over several WebSocket messages, and one WebSocket message can
contain several packets. The protocol's own decoder sorts that out. If you
need to know where each WebSocket message begins and ends, use the frame API
instead.

### Installing the filter

On the server, send the `101` upgrade response first, then add the filter:

```rust
let io = ntex::ws::WsTransport::create(io, ntex::ws::Codec::new());
```

You can pass the resulting `Io<Layer<WsTransport, F>>` straight to a protocol
service, or call `io.boxed()` if the service expects type-erased I/O. To add
the filter as a step in a service pipeline, use [`WsTransportService`]
instead: `WsTransportService::new(ws::Codec::new())`. Either way, the HTTP
handshake must already be done.

On the client, convert the connection returned by `WsClient`:

```rust
let io = connection.into_transport();
```

This keeps the client's codec, along with its masking mode and any compression
negotiated during the handshake. A fresh codec would use the server's masking
rules, which is wrong for a client. From here on, the inner protocol owns the
stream. Don't keep using an old frame sink alongside it; that would mix two
different ways of writing to the same connection.

The [I/O filter subsystem](./7-io.md#filter-subsystem) section explains how
filters work with TLS, buffering, backpressure, and shutdown.

### MQTT over WebSocket

The [MQTT-over-WebSocket example] shows all of this in practice, with a server
and a client built on `ntex-mqtt`. Both speak MQTT 3.1.1 and use the standard
`mqtt` subprotocol.

The server accepts upgrades only on `/mqtt`, and only from clients that offer
`mqtt`. After checking the handshake, it selects `mqtt` in its `101`
response, stops the HTTP timer, and installs `WsTransport`. It then hands the
boxed stream to `v3::MqttServer`, which handles CONNECT and incoming
publishes. The server is deliberately minimal: it receives publishes, but it
isn't a broker, so it doesn't manage subscriptions or forward messages.

The client offers `mqtt` with `WsClientConfig::set_protocols()` and checks
that the server picked it. A custom connector for `v3::client::MqttConnector`
returns `connection.into_transport()` instead of a plain socket. As far as the
MQTT client is concerned, this is just another stream: it sends CONNECT and
exchanges packets as usual.

When you run the client, it sends a QoS 1 publish and waits for the
acknowledgement. The MQTT dispatcher runs at the same time so it can read
that acknowledgement. The client then closes the MQTT session and lets the
transport shut down. Keepalive is still MQTT's job; WebSocket ping/pong is a
separate mechanism and doesn't replace it.

### AMQP over WebSocket

The same approach works for AMQP 1.0, whether you're serving `ntex-amqp` or
connecting through a custom client connector. The [AMQP WebSocket binding]
uses `amqp` as its subprotocol, and both sides should check that it was
negotiated.

The binding has one rule to watch for at the start of the connection: each
opening AMQP protocol header must travel in a WebSocket message of its own.
That includes the SASL header, if SASL is used. After the headers, AMQP frames
can span messages or share them freely.

`WsTransport` has no idea where an AMQP protocol header begins or ends, so the
filter alone doesn't enforce this rule. Your AMQP handshake integration has to
keep each header in its own message, and you should test it against the peer
you plan to use.

Everything else, including authentication, sessions, links, idle timeouts, and
orderly shutdown, is still handled by the AMQP implementation. If you need
TLS, use `wss://` for the WebSocket connection rather than negotiating TLS
inside the AMQP stream.
